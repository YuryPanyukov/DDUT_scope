# Оценочный комитет

[![CI](https://github.com/YuryPanyukov/DDUT_scope/actions/workflows/ci.yml/badge.svg)](https://github.com/YuryPanyukov/DDUT_scope/actions/workflows/ci.yml)
[![Release](https://github.com/YuryPanyukov/DDUT_scope/actions/workflows/release.yml/badge.svg)](https://github.com/YuryPanyukov/DDUT_scope/actions/workflows/release.yml)

Desktop-приложение для администратора: собирает оценки преподавателей из Excel-файлов,
объединяет баллы учеников по ФИО, сортирует результаты, экспортирует итоговые таблицы
и сохраняет проект в JSON.

Проверено в работе с реальными файлами преподавателей ДДЮТ (см. «Поддерживаемые форматы»).

| Параметр | Значение |
|---|---|
| Язык | Python 3.11+ |
| GUI | PyQt5 |
| Excel | openpyxl |
| Хранение проекта | JSON |

## Установка и запуск

Через `uv` (так настроен репозиторий — есть `uv.lock` и `.python-version` = 3.11):

```bash
uv sync          # создаст .venv, установит PyQt5, openpyxl и dev-инструменты
uv run main      # консольная команда приложения
# равнозначно: uv run main.py, uv run python main.py, uv run python -m evaluation_app
```

Через `pip`:

```bash
python -m venv .venv
source .venv/Scripts/activate        # Windows (Git Bash)
pip install -r requirements.txt      # PyQt5, openpyxl
python main.py                       # или: python -m evaluation_app.main
```

### Про зависимости

* Проект ставится как пакет (`hatchling`), поэтому доступна команда `main` и `uv run`
  работает без указания пути к файлу.
* В `pyproject.toml` есть ограничение `PyQt5-Qt5<5.15.3; sys_platform == "win32"`:
  Qt 5.15.3+ не публикуется колёсами для Windows, и без этого ограничения разрешение
  зависимостей выбирает `pyqt5-qt5 5.15.19`, из-за чего на Windows окружение не собирается
  («no matching distribution / no wheel for the current platform»), и `uv run` падает ещё
  до запуска приложения. На Linux и macOS ограничение не действует.
* Dev-инструменты (`pytest`, `ruff`) описаны в `[dependency-groups] dev` и ставятся
  обычным `uv sync`.

Если зависимости менялись, обновляйте замок: `uv lock`, затем `uv sync`.

## Сборка exe для Windows

```bash
uv sync --group build                          # PyInstaller (при обычном uv sync не ставится)
uv run --group build python scripts/build_exe.py
```

Результат в каталоге `dist`:

* `dist/DDUT-Scope/DDUT-Scope.exe` — приложение одной папкой (запускается быстрее, чем onefile,
  и реже попадает под ложные срабатывания антивирусов);
* `dist/DDUT-Scope-<версия>-windows-x64.zip` — та же папка плюс файл «Как запускать.txt».

Сборка возможна только на Windows: PyInstaller не кросс-компилятор. Имя файла — латиницей
(`DDUT-Scope`), а название «Оценочный комитет» показывается внутри приложения; имя задаётся
константой `APP_NAME` в `scripts/build_exe.py`. Иконка `evaluation_app/resources/icons/app.ico`
встраивается в exe и копируется рядом с ним, чтобы её видело и само окно. Каталоги `dist/` и `build/`
в репозиторий не попадают.

### Иконка

Иконка лежит в репозитории (`app.ico` для Windows и exe, `app.png` — запасной вариант для
систем, где Qt не читает ICO) и подключена к `QApplication` и главному окну. Перерисовать её
в другом цвете или с другими пропорциями можно скриптом:

```bash
uv run python scripts/create_icon.py   # обновит app.ico и app.png
```

Иконка рисуется средствами самого PyQt5, поэтому Pillow или другие графические
библиотеки проекту не нужны. Цвета, отступы и размеры внутри иконки задаются константами
в начале `scripts/create_icon.py`.

Пробные файлы обоих форматов и шаблон для преподавателей:

```bash
uv run python scripts/create_samples.py   # файлы появятся в каталоге samples/
```

## Поддерживаемые форматы Excel

### 1. Таблица «строка = оценка» (шаблон из плана)

Обязательные столбцы: `ФИО`, `Итого`; необязательный — `Название конкурса`.
Названия и порядок столбцов не важны: подписи распознаются по синонимам
(«ФИО» / «Ученик» / «Фамилия Имя Отчество» / «Обучающийся», «Итого» / «Баллы» / «Сумма»,
«Название конкурса» / «Конкурс» / «Мероприятие» / «Номинация»). Баллы читаются как числа,
как текст («85,5», «12 баллов», «1 000»), пустые и итоговые строки пропускаются;
пустая ячейка баллов у строки с ФИО считается 0 баллов (ученик не теряется из-за нуля).

| ФИО | Название конкурса | Итого |
|---|---|---|
| Иванов Иван | Олимпиада по математике | 85 |

### 2. Оценочный лист-матрица (фактический формат файлов преподавателей)

```
ряд 1:   ФИО | за вход в систему | УЧЕБНАЯ И ПРОЕКТНАЯ ДЕЯТЕЛЬНОСТЬ | ... | ИТОГО
ряд 2:       |                   | Участие (внутренний) | Призовое место (внутреннее) | ...
ряд 3:       | 30                | 30 | 40/50/60 | ...
ряд 4+:  Соколова Наталья Фёдоровна | 10 | 10 | 5 | 0 | 30 | 0 | 45
```

Особенности, которые приложение учитывает автоматически:

* шапка занимает 1–6 строк: группы направлений, названия критериев и строка максимумов;
* названием критерия считается подпись из строки-подписи, а не «30»/«40/50/60» из строки максимумов;
* строки нумерации столбцов (`1, 2, 3, ...`) распознаются и не мешают поиску шапки;
* служебные столбцы («№», «класс», «педагог», «примечание» и т. п.) критериями не считаются
  и в сумму не входят; при этом критерии вида «Очное участие в мастер-классах» — обычные критерии;
* баллы служебного столбца «за вход в систему» входят в итог ученика отдельной оценкой, если
  формула `ИТОГО` их не учитывает — так бывает в файлах-шаблонах (`=SUM` не включает первый
  столбец), и о каждом таком случае парсер сообщает предупреждение;
* баллы ученика = сумма его критериев (+ баллы столбца «за вход в систему», см. выше);
  если на листе есть колонка `ИТОГО`, она используется
  как контрольная: при расхождении в проект идёт значение из файла, а расхождение попадает
  в предупреждения; незаполненная (нулевая) колонка ИТОГО обнулять баллы не даёт;
* ученик без единого балла (все критерии и `ИТОГО` = 0 или пусто) попадает в сводную таблицу
  с результатом 0 баллов, а не отбрасывается;
* листы с тысячами «фантомных» пустых строк разбираются быстро (итерация прекращается
  после 100 строк подряд без ФИО).

Название преподавателя по умолчанию берётся из имени файла и приводится к виду
«Оценки_Петрова_2025.xlsx» → **Петрова**.
В диалоге импорта его можно изменить или отметить лист как «пропустить».

## Порядок работы

1. **Создать шаблон** — «Файл → Создать шаблон Excel...», передать преподавателям.
2. **Импорт** — «Файл → Импорт Excel...» (`Ctrl+I`). Файлы читаются в фоновом потоке
   с индикатором прогресса (кнопка «Отмена» прерывает разбор), после чего открывается
   предпросмотр: каждый лист, режим разбора, структура столбцов, количество строк,
   сумма баллов, предупреждения и привязка «лист → преподаватель».
3. **Сводная таблица** — баллы суммируются по ФИО ученика по всем преподавателям и направлениям
   (регистр и лишние пробелы не важны). Доступны сортировка (клик по заголовку столбца или список
   «Сортировка») и поиск по ФИО.
4. **Детали** — при выборе преподавателя слева показывается матрица «ученики × критерии»:
   строки — ученики направления, столбцы — критерии (конкурсы), последний столбец —
   итоговая сумма баллов ученика; строка направления показывает его общий итог.
   Клик по заголовку «Направление / ФИО» сортирует учеников по алфавиту, по заголовку
   «Итого баллов» — по сумме (по убыванию, как в сводной), повторный клик меняет
   направление; по столбцам критериев сортировка не работает — ячейки текстовые.
5. **Столбцы** — во всех таблицах (сводная, матрица преподавателя, предпросмотр импорта)
   столбцы можно перетаскивать за заголовок и менять их ширину перетаскиванием границы.
   ПКМ по названию столбца открывает меню: «Скрыть столбец …» прячет столбец, на котором
   вызвано меню, «Показать все скрытые столбцы» возвращает все скрытые. В матрице
   преподавателя скрытие переживает смену преподавателя и сортировку.
6. **Обновление данных** — «Обновить из Excel» у выбранного преподавателя: старые данные
   заменяются новыми после подтверждения.
7. **Сохранение** — проект сохраняется в JSON (`Ctrl+S`) и открывается через «Файл → Открыть проект...».
8. **Экспорт** — сводная таблица (`Ctrl+E`), весь проект (лист «Сводная» + лист на каждого
   преподавателя, где после строк каждого ученика идёт его «Итого по ученику») или данные
   одного преподавателя.
9. **Отмена изменений** — `Ctrl+Z` (до 20 шагов).

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Файл не найден / не .xlsx | Диалог с описанием ошибки, файл пропускается |
| Файл .xls (старый Excel) | Подсказка сохранить файл как .xlsx |
| Структура листа не распознана | Предлагается диалог: строка заголовков, столбцы и режим разбора (таблица или лист-матрица) |
| Нет обязательных столбцов | То же — ручное указание столбцов или пропуск листа |
| Пустые строки, повторные заголовки, строки «ИТОГО» | Пропускаются, учениками не становятся |
| Пустая ячейка баллов у строки с ФИО | Ученик попадает в таблицу с 0 баллов (с предупреждением) |
| Текст вместо числа в баллах | Строка (или ячейка) пропускается с указанием номера строки |
| Формула `ИТОГО` не учитывает столбец «за вход в систему» | Баллы столбца прибавляются к итогу, есть предупреждение |
| Дублирующиеся ФИО | Баллы автоматически суммируются |
| Лист «Общий свод», файл со ссылками на другие книги | Предупреждение о риске двойного учёта баллов |
| Повреждённый/отсутствующий JSON | `ProjectError` → диалог с сообщением |

## Тесты и линтер

```bash
uv run pytest          # или: python -m pytest
uv run ruff check .    # линтер, настройки в [tool.ruff] внутри pyproject.toml
uv run vulture         # мёртвый код, настройки в [tool.vulture] внутри pyproject.toml
```

`vulture` ищет определения, которые нигде не вызываются. Настройки и список
известных ложных срабатываний (методы-переопределения Qt, фикстуры pytest,
атрибуты ячеек openpyxl) заданы в `[tool.vulture]` в `pyproject.toml`.

Порог уверенности (60%) — минимальный: ровно с такой уверенностью `vulture`
сообщает о неиспользуемых функциях, классах, методах и свойствах, а выше этого
значения они молча пропускаются. В исключениях нет шаблонов, поэтому новое
мёртвое определение не может проскочить через CI. Минимальность порога,
охват пакета и отсутствие шаблонов в исключениях закреплены в
`tests/test_packaging.py`.

Скан в CI включает и тесты, поэтому API, нужное только тестам, мёртвым не
считается. Чтобы это было видно явно, у такого определения в docstring есть
фраза «Используется только в тестах» с пояснением, чем метод заменён в
приложении. За этим следит тест `test_definitions_without_callers_are_marked_as_test_only`:
он повторяет скан без тестов и требует пометку от каждого определения,
оставшегося без вызовов.

Покрыты: модели и сериализация, разбор Excel (в том числе шапка в несколько строк, лист-матрица
с критериями и колонкой ИТОГО, служебные столбцы, расхождение с ИТОГО, пустые и итоговые строки,
«фантомные» строки, ручные настройки столбцов), агрегация и статистика, сортировка,
сохранение/загрузка проекта, экспорт и шаблоны, интерфейс в offscreen-режиме Qt.
Часть тестов дополнительно прогоняет парсер на реальных файлах, если каталог с ними доступен.

## Непрерывная интеграция

`.github/workflows/ci.yml` запускается на каждый push и pull request в двух окружениях
(Ubuntu и Windows, Python 3.11) и повторяет установку «с нуля»:

1. `uv lock --check` — `uv.lock` соответствует `pyproject.toml`;
2. `uv sync --frozen` — чистая установка ровно по `uv.lock`, без обновления зависимостей;
3. `uv run --frozen ruff check .` — линтер (на Linux);
4. `uv run --frozen vulture` — поиск неиспользуемых определений (на Linux);
5. `uv run --frozen pytest` — тесты.

Те же шаги можно повторить локально, это и есть проверка чистой установки:

```bash
rm -rf .venv
uv lock --check && uv sync --frozen
uv run --frozen ruff check . && uv run --frozen pytest
```

Windows-раннер держится в матрице специально: он ловит регрессию с ограничением
`PyQt5-Qt5<5.15.3` (см. «Про зависимости»), из-за которой окружение раньше вообще не собиралось.
Тесты GUI идут в offscreen-режиме Qt, поэтому на раннере окна не открываются.
Каталог `real_data/` в репозиторий не попадает, поэтому тесты на реальных файлах в CI пропускаются.

Отдельный job `build-windows` запускается после успешных тестов, собирает exe тем же скриптом,
проверяет дымовым запуском, что приложение стартует, и выкладывает архив артефактом
`DDUT-Scope-windows` (хранится 14 дней) — скачать его можно со страницы прогона workflow.

## Непрерывная доставка (релизы)

`.github/workflows/release.yml` — второй workflow: он собирает exe и публикует архив
на GitHub Releases, где он доступен постоянно, а не 14 дней, как артефакт CI-прогона.

Триггеры:

* **push тега `v<версия>`** (например, `v1.0.0`) — обычный релиз-путь: собрать exe,
  проверить его дымовым запуском и опубликовать;
* **workflow_dispatch** — ручной запуск со страницы Actions для повторной публикации
  той же версии: если релиз `v<версия>` уже существует, архив заменяется на свежий,
  заметки релиза при этом не изменяются.

Перед публикацией workflow сверяет тег с версией из `pyproject.toml` (`git tag v1.0.0`
проходит только при `version = "1.0.0"`): имя релиза и имя архива берутся из этой
версии, и расхождение с тегом делало бы релиз с одним номером, а архив — с другим.
Несовпадение — падение шага, без публикации архива.

Release-задача не гоняет тесты (их делает `ci.yml`), поэтому обычный
путь такой: сначала дождитесь зелёного CI на коммите, и только потом снимайте с него тег.

Порядок выпуска версии:

```bash
# 1. Поднимите версию в pyproject.toml ([project] version = "1.1.0")
#    и обновите замок: uv lock
# 2. Дождитесь зелёного CI на коммите с новой версией.
# 3. Снимите и запушьте тег (он обязан совпасть с версией: v1.1.0 ↔ version = "1.1.0"):
#
git tag v1.1.0
git push origin v1.1.0
#
# 4. В «Releases» появится релиз DDUT-Scope 1.1.0 с архивом
#    DDUT-Scope-1.1.0-windows-x64.zip и автозаметками (--generate-notes).
```

Ручной перезапуск (workflow_dispatch) не создаёт дублей: если релиз этой версии есть,
